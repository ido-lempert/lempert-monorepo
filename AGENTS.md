## WebstormProjects

Nx monorepo (npm, `nx@23.2.1`) hosting multiple separate, unrelated products — each its own app/lib, not one shared product. Per-product planning docs (briefs, PRDs, architecture) land under `_bmad-output/planning-artifacts/`; deeper project knowledge goes in `docs/`.

## Where things are

- Per-product planning artifacts: `_bmad-output/planning-artifacts/`
- Project knowledge / deeper docs: `docs/`

## Running and verifying

- Apps live in `apps/*` as npm workspaces; Nx infers targets from each app's `package.json` scripts.
- `mancala` (3D Kalah in the browser, Vite + three.js):
  - dev server: `npx nx run mancala:dev` (http://localhost:5173, also exposed on the LAN for phone testing)
  - tests: `npx nx run mancala:test` (vitest, rules engine)
  - typecheck + production build: `npx nx run mancala:build` (output `apps/mancala/dist`)
  - production server (static `dist/` + multiplayer WebSocket on one port, `PORT` default 8080): `npx nx run mancala:start` after build
  - online multiplayer: the server in `apps/mancala/server/` is authoritative (validates moves); in dev it runs inside the Vite server via a plugin, at `/ws`

  - board layout: sowing is clockwise with each player's store on their left; the rules engine is index-based (`src/game/kalah.ts`) and only `containerCenter` in `src/render/board3d.ts` decides placement

- `archipelago` (3D puzzle game that teaches software architecture to teens and adults, Vite + three.js PWA, offline):
  - dev server: `npx nx run archipelago:dev` (http://localhost:5176, also on the LAN)
  - tests: `npx nx run archipelago:test`; typecheck + build: `npx nx run archipelago:build`
  - the concept and the slice plan live in `_bmad-output/planning-artifacts/archipelago/`; developed in vertical slices
  - the mechanic: place pieces from the tray on pads, tap a piece then another to draw a pipe (an edge A→B = A calls B, the dependency direction), press run and critters carry each request along the pipes; a solved level wins a concept card (term in Hebrew and English) for the blueprint book
  - `src/game/` is pure and tested: levels (`levels.ts`, each with a `solution` the tests run), the simulation (`sim.ts`: paths, rules, fail reasons `noPath` / `reversed` / `shape` / `exposedDb` / `twoAddresses` / `overload` / `tooSlow`; flows can send `count` requests, levels can set `capacity` per server and a `timeLimit` where the database costs `DB_TIME` and a cache hit `HIT_TIME`; BFS prefers the least busy piece, which is how a load balancer spreads work; `events` are one-way messages copied to every subscriber (paper planes in `Board.flight`), a `queue` in front of a worker stops it dropping messages; islands are `ISLANDS` / `levelsOf` in `levels.ts`, `groundAt(z, island)` gives terraces only on island 1), plugs (`pieces.ts`), saves (`progress.ts`, migrations in `parseProgress`); `src/world/` renders (`board.ts` = a level and the run animation, `models.ts` = every model, procedural, `look.ts` = materials, `world.ts` = renderer, camera, picking); `src/main.ts` wires the UI
  - island 3, the patterns workshop (`ISLANDS = [1,2,3]`, wooden deck via `DECK` in `groundAt`): `LevelDef.gates` (`{target, via}`: only `via` may call `target`, else `unguarded` = Proxy), `LevelDef.single` (kinds allowed once, else `duplicate` = Singleton), `Flow.toKind` (aim at any piece of a kind, pinned to the one reached) and `Flow.via` (wrappers the path must cross, else `unwrapped` = Decorator/Middleware); wrapper pieces are `WRAPPERS` in `pieces.ts` (lock, zip) and `Board.wrap` draws them on the critter; Strategy, Factory and Observer don't fit the request graph and are not built yet
  - island 4, the onion (Clean Architecture): `RING` in `pieces.ts` gives each kind a ring (entity 0, usecase/port 1, controller 2, outside 3), rule `inward` makes an edge from a lower ring to a higher one an `outward` problem, `Pad.ring` makes a piece of another ring a `wrongRing` problem, `Gate.fail` picks the reason a gate reports (`skipsLayer`); an `IMPLEMENTERS` piece (db, email) drawn to a `port` is an implementing edge: drawn inward, exempt from gates, and swapped to port → implementer in `run`; the rings are floor decoration in `models.ts` (`RINGS`)
  - archipelago copy: technical terms stay in English inside the Hebrew text (names, level titles, goals, fails, concept cards; the tag's big line is the English name, the small line a few Hebrew words), and each level goal states the problem precisely, with a business scenario; every piece acts out its job when a request reaches it (`BEHAVIOUR` in `world/board.ts`: a jargon label such as `SELECT` or `HIT` and a move; `Board.behave`, and a cache stores a copy on the way back in `Board.store`), so new kinds need an entry there
  - archipelago symbols: pieces carry the industry-standard notation where one exists (`apps/archipelago/src/glyphs.ts`, inline SVG, `glyph(kind)`: UML lollipop for a Port, UML use-case ellipse, cylinder for a database, and so on), shown next to the English name on the in-world tags and the tray buttons; a new kind needs an entry in `PATHS`
  - UI text is Hebrew only for now, in `src/i18n/strings.ts`; plural address, infinitives on buttons, failures in one short line; teach while playing (the first level's walkthrough is `tutorialStep` in `main.ts`, one-time tips via `firstTime`)
  - deployed as a Render static site (`archipelago` in `render.yaml`), from `main`: work on the `archipelago` branch, merge to `main` to release
  - music (`src/audio.ts`): a generated calm marimba loop with its own menu toggle; effects are synthesised too
  - in dev, `window.__game` (start, place, connect, run, solve, screenOf) lets Playwright drive the game

## Conventions that differ from defaults

- Every project added here is TypeScript, using npm as the package manager — don't introduce another language or package manager without updating this file.
- Projects are independent products with separate users and roadmaps — don't assume shared code, dependencies, or release cadence between them unless a shared lib is deliberately created.
